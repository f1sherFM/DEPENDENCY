# DEPENDENCY 0.6.0 — Impact Analysis

Статус: принят и реализован в 0.6.0. Основа — версия 0.5.0. Проверки и практические ограничения описаны в [version-0.6-validation.md](version-0.6-validation.md).

Уточнения реализации: рисунок результатов ограничен текущей страницей и явно обозначен как её проекция; отдельное действие показывает сегмент доказательного пути. Память индекса ограничивается консервативной оценкой 256 МиБ, чтение JSON — 64 МиБ; это не лимит RSS процесса. Ответы последовательных вычислений сохраняются в одном immutable cache, отдельный job scheduler и отмена backend не добавлены. Версии parser/resolver/rules и схема SQLite не изменены.

## Цель и смысл результата

Для выбранного файла показать прямых и транзитивных потребителей в сохранённом графе, глубину распространения и проверяемую цепочку импортов до каждого результата. Работать без повторного анализа проекта и без доступа к его текущим исходникам.

Формулировка результата: «Может быть затронут по известным зависимостям снимка». Достижимость — подтверждённый факт графа; влияние конкретного изменения — предположение. Файловый граф пока не знает, какой экспорт изменился, какие символы использует потребитель, выполнится ли ветвь программы и сломается ли сборка.

Не вводить общий балл риска. Показать отдельные факторы: число уникальных прямых/транзитивных потребителей, глубину, типы импортов, связь с известными циклическими компонентами и кандидатов тестов. Количество затронутых публичных интерфейсов пока вычислить нельзя.

## Текущая реализация и необходимые изменения

- `src/graph.ts` умеет только ближайшее окружение выбранного узла. Это frontend-проекция с лимитами 200 узлов/1 000 стрелок; использовать её как вход Impact Analysis нельзя.
- Полный граф хранится в SQLite JSON-снимке. `GraphEdge` содержит source, target, kind и line — достаточно для обхода и доказательной цепочки.
- `diagnostics.rs` уже находит SCC и сохраняет coverage-метаданные. Их можно использовать как контекст, не заменяя обход графа списком диагностик: правила могут быть отключены или исключены конфигурацией.
- Tauri уже запускает тяжёлые операции в `spawn_blocking`. Для первых bounded-запросов отдельный универсальный job scheduler не нужен.
- Package-рёбра сейчас имеют kind=`package` и не сохраняют исходную классификацию import/type-only/dynamic. Поэтому в первом объёме стартовать анализ от внешнего npm-пакета не предлагаем: такой старт потребовал бы уточнения контракта рёбер.

## Объём первой реализации

1. Один выбранный локальный файл как исходная точка, включая импортируемый ресурс (например, CSS). Дополнительно поддержать до 32 явно выбранных файлов одним запросом; каталог можно добавить позднее через явное раскрытие в исходные файлы.
2. Прямые и транзитивные потребители, минимальное расстояние до любой исходной точки, одна кратчайшая цепочка-обоснование.
3. Режим всех известных локальных импортов по умолчанию и режим статических исполняемых импортов; произвольная комбинация известных типов рёбер — через явные фильтры.
4. Список результатов, поиск и роль «кандидат теста», связь с графом и деталями пути. Возврат в обычный граф сохраняет выбранный snapshot.
5. Работа на исторических снимках, включая legacy, с явным указанием версии анализатора и неполноты метаданных покрытия.

Анализ изменения конкретного экспорта, Git diff/веток, сопоставление снимков, исполнение тестов и прогноз фактической поломки не входят в 0.6.0.

## Направление обхода и доказательства

Исходное ребро `A → B` означает «A импортирует B». При изменении B обход идёт по reverse adjacency к A, затем к потребителям A. Обход обычных outgoing-связей отвечает на вопрос «от чего зависит B» и не смешивается с impact.

Алгоритм: итеративный multi-source BFS по входящим рёбрам полного снимка. Индексы incoming/outgoing строятся один раз; фильтрация по типам рёбер выполняется до расширения frontier. visited предотвращает повторную обработку циклов. Сложность построения индекса и обхода — O(V+E); перечислять все пути нельзя.

- Исходные точки включены в visited с distance=0 и показываются отдельным списком; в счётчик затронутых потребителей не входят, даже если цикл возвращается к ним.
- Для каждого найденного потребителя хранить минимальное расстояние и одно parent edge до уже найденного узла. При нескольких кратчайших вариантах выбирать детерминированно: sorted roots и рёбра по source/target/kind/line/id.
- Доказательство отображается в исходном направлении импортов: `consumer → … → changed-file`. Каждое звено берётся из снимка, со строкой и kind. Внутренний порядок BFS не выдаётся за направление импорта.
- Одна цепочка подтверждает достижимость; она не описывает все пути и не доказывает отсутствие альтернативных type-only/dynamic связей.
- Результат для нескольких исходных точек — объединение без двойного счёта. `viaRootId` показывает корень выбранного свидетельства; не утверждать, что это единственный достижимый корень.
- direct: distance=1; transitive: distance>1. Максимальная глубина — максимальное минимальное расстояние в выбранном графе, не максимальная длина всех возможных путей.

Случаи A→B→C, при выборе C: B — direct, A — transitive, путь A→B→C. При выборе A потребителей нет, хотя A зависит от B и C.

## Режимы и ограничения достоверности

`all` включает `import`, `reexport`, `commonjs_import`, `type_only_import`, `dynamic_import`; внешние package-рёбра не обходятся. `static` включает первые три вида. Пользователь может задать конкретный набор известных видов; неизвестные значения не игнорировать молча.

Type-only путь означает потенциальную зависимость типов; dynamic import — статически найденную возможность загрузки. Ни то, ни другое не гарантирует выполнение кода. При смене фильтра меняются сам обход, counts и evidence; это не просто скрытие стрелок после вычисления.

Поиск по названию/пути и отображение только тестов фильтруют уже найденные результаты и не обрывают промежуточные пути. Это отдельные фильтры представления. Исключения `dependency.config.json` для диагностик на impact не влияют.

Кандидатов тестов определять консервативно по `*.test.*`, `*.spec.*` и каталогам `test/tests/__tests__`; это соглашение об имени, не доказательство исполнимости и не рекомендация, какие тесты достаточно запустить. Счётчик тестов — подмножество уникальных потребителей.

Из 0.5 брать сведения о parse/read/resolution gaps и пропущенных правилах. Отключённое правило не означает плохое покрытие графа, а выключенная карточка coverage не устраняет известный gap. Для legacy использовать доступные счётчики и явно отмечать, что полных метаданных нет. Нулевая известная достижимость при таком покрытии не означает «изменение безопасно».

Legacy parser-1 может неверно классифицировать type-only экспорты. Разрешить запрос к его сохранённому графу с заметным предупреждением; не переинтерпретировать историю по текущему коду или настройкам проекта.

## Контракт backend

Новый модуль `impact.rs`: чистое ядро обхода над графом, построение доказательств и небольшой слой bounded-запросов. Не запускать resolver/parser/rules заново и не читать исследуемые файлы ради запроса.

```text
ImpactRequest {
  snapshotId, roots[], edgeKinds[], maxDepth: integer | null
}

ImpactSummary {
  queryId, snapshotId, impactVersion, analyzerVersion, rulesVersion,
  roots[], effectiveEdgeKinds[], maxDepth,
  status: complete | partial,
  partialReasons[], knownAffectedCount, knownDirectCount,
  knownTransitiveCount, knownTestCandidateCount, maxKnownDistance,
  coverage: { state: known-gaps | no-recorded-gaps | legacy-unknown, reasons[] },
  visitedNodeCount, examinedEdgeCount, elapsedMs,
  firstPage: ImpactPage
}

ImpactRow { nodeId, distance, viaRootId, isTestCandidate, hasRecordedCycleDiagnostic }
ImpactPage { items[], offset, nextOffset, knownMatchingCount, status }
ImpactPath { edges[], offset, nextOffset, totalEdgeCount, reachesRoot }
```

`hasRecordedCycleDiagnostic=false` не означает отсутствия цикла: правило могло быть выключено. В интерфейсе показывать только положительный контекст «есть сохранённая диагностика цикла»; не выводить «циклов нет» из этого поля.

Команды: `get_impact(request)`, `get_impact_page(queryId, offset, limit, text, testsOnly)`, `get_impact_path(queryId, nodeId, offset, limit)`. Чистые фильтры списка входят в page-запрос, а параметры обхода — в ImpactRequest. Сортировка результатов: distance, relative path, nodeId.

Валидировать snapshot, непустые уникальные roots из того же снимка, разрешённые edgeKinds, диапазон maxDepth=1..64 или null. Неподдерживаемый kind, неизвестный узел, npm-узел, смешение снимков и превышение 32 корней возвращают понятную ошибку. Удаление текущего проекта на диске не мешает запросу по снимку.

## Объём работы, ответы и кэш

Не хранить полный путь у каждого результата: parent links занимают O(V), пути восстанавливаются по запросу. Не возвращать весь подграф по IPC одним payload.

Предлагаемые начальные пределы, подлежащие проверке на больших fixtures:

- Точный обход до 100 000 посещённых узлов, 1 000 000 проверенных рёбер и двух секунд самого обхода. Чтение JSON и построение индекса измерять отдельно; таймер обхода нельзя выдавать за лимит полной задержки.
- Страница до 200 строк; путь выдаётся последовательными сегментами до 200 рёбер. Разрыв пути показывается явно, последний сегмент отмечает достижение исходной точки. Не замыкать обрезанный маршрут фиктивной стрелкой.
- При depth/budget limit возвращать status=partial с причиной. Если frontier пуст и все допустимые рёбра проверены, результат complete даже при совпадении численного лимита. Counts частичного результата — нижние границы («найдено не менее N»), а не точное число всех затронутых файлов.
- Лимит рисунка 0.4 отделён от обхода: вычисленный полный результат может содержать гораздо больше узлов, чем изображение. Сообщать отдельно «не исследовано» и «не показано»; количество неизвестных потребителей при незавершённом обходе вычислить нельзя.

Для страниц и путей держать в памяти один последний immutable индекс снимка и последний результат запроса, общий через `Arc` в состоянии приложения. Ключ: snapshotId + impactVersion + нормализованные roots/edgeKinds/maxDepth. Бюджеты также фиксируются в метаданных результата. Новый query не мутирует уже выданный результат.

Ограничить память кэша; если даже индекс не помещается, вернуть явную ошибку объёма вместо усечения графа. При вытеснении queryId последующая страница получает «результат истёк, повторите запрос». Не читать другой snapshot по устаревшему курсору. До выбора предела памяти измерить размер индекса; ориентир для первой реализации — один индекс/результат, а не безразмерный map всех снимков.

UI использует generation/request token: ответ старого запроса не заменяет новый выбранный snapshot/узел. Отмена показа не гарантирует немедленного прерывания backend; работа ограничена бюджетами. Если измерения покажут неприемлемую задержку, добавить адресную отмену обхода, не вводя общий scheduler заранее.

Результаты запросов не требуют новой таблицы SQLite: они выводятся из неизменяемого сохранённого графа. После перезапуска повторяется дешёвый обход, а не анализ исходников. Версии parser/resolver/rules из-за добавления impact не повышаются без самостоятельной причины.

## Интерфейс

В контексте файла — действие «Анализ влияния». Открывается режим с исходной точкой, идентификатором/датой снимка, режимом рёбер, глубиной и статусом полноты. Смена snapshot сбрасывает запрос и выборку.

Сводка: прямые/транзитивные потребители, тестовые кандидаты и глубина. Таблица с поиском: файл, расстояние, выбранный корень, роль теста, действие «Почему затронут». В панели evidence — кликабельные звенья реального пути и оговорки покрытия. Сохранённые диагностики цикла доступны как дополнительный контекст.

Граф получает явно найденный набор nodeIds и исходные точки с отдельным выделением. Направление стрелок остаётся исходным. Первое действие «Показать путь» отдаёт небольшой доказательный подграф; «Показать результаты» включает ограниченную проекцию всей выборки с честными счётчиками скрытых элементов. Для больших наборов сам рисунок не должен требовать передачи всех рёбер frontend заново; повторно использовать уже открытый снимок и bounded path/page-ответы.

Пустой результат: «В выбранном графе не найдены потребители». При partial/coverage gaps это сопровождается причиной, без зелёного вердикта безопасности.

## Последовательность реализации и проверки

1. Чистый reverse BFS и parent evidence; тесты цепи, ромба, нескольких корней, самоссылки, SCC и изолированного файла. Проверять каждое ребро доказательства и минимальное расстояние, исходные точки не входят в counts.
2. Фильтры типов: runtime/type-only/dynamic, reexports/barrels, смешанные и альтернативные пути. Поиск/тестовый фильтр не должны отсекать промежуточные узлы обхода.
3. Snapshot API и bounded index/result cache: исторический снимок, удалённый root на диске, отключённые правила 0.5, legacy metadata, недопустимые IDs, истёкший queryId и смена снимка во время запроса.
4. Пагинация, длинные пути и лимиты: цепь 50 000 файлов, широкое дерево, плотный циклический граф; отдельно exact/depth-limited/budget-limited. Проверять суммарные counts, отсутствие дублей и честное обозначение неизвестного остатка.
5. UI и граф: направление стрелок, «Почему затронут», несколько корней, пустой результат, большие выборки, фильтры, возврат в граф и история. Browser smoke плюс запуск Windows-сборки; ограничения нативной UI-проверки документировать отдельно.
6. Регрессии 0.3–0.5: правила и snapshots не меняются от impact-запросов, AST не разбирается повторно. На нескольких реальных проектах вручную сверить выбранные пути, записать покрытие, время чтения/индекса/обхода, память и размеры ответов.

Критерий готовности: каждый найденный потребитель имеет проверяемую цепочку до одной из исходных точек в выбранном snapshot; полный результат точен для выбранных рёбер, неполный явно помечен; ограничения UI не меняют расчёт; исторические данные остаются неизменными. Вывод «это изменение сломает эти файлы» инструмент пока не делает.
