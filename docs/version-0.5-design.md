# DEPENDENCY 0.5.0 — архитектурная диагностика

Статус: принят; реализован в 0.5.0. Проверки и практические ограничения — в [version-0.5-validation.md](version-0.5-validation.md).

Уточнения реализации: классификация `export type` и inline type specifiers потребовала `js-ts-parser-2`, поэтому старый кэш обновляется один раз. При изменении только rules/config новый кэш переиспользуется. Стартовые настраиваемые пороги — fan-out >20, fan-in >30; двух небольших реальных проектов недостаточно для универсальной калибровки. Неполное покрытие или невозможность прочитать package entry points пропускают правило consumers с явной причиной.

## Цель

По полному графу снимка объяснять архитектурные риски: где есть циклы, какие файлы имеют много связей и какие исходники требуют проверки на отсутствие потребителей. Каждая диагностика должна иметь проверяемое основание, область действия и ограничение достоверности. Ограничения рисунка графа из 0.4 не влияют на результаты правил.

## Текущая основа и ограничения

- Rust строит полный файловый граф и извлекает импорты через Tree-sitter; resolver учитывает конфигурацию JS/TS.
- `find_cycles` использует итеративный Kosaraju и возвращает отсортированные сильно связанные компоненты (SCC), включая самоссылки. SCC не задаёт последовательность импортов. Сейчас ProblemsView соединяет её элементы стрелками; в 0.5 это представление необходимо исправить.
- Диагностики разрешения импортов уже имеют причину, файл, строку и подсказку. Ошибки разбора представлены только общим счётчиком, поэтому для точных ссылок потребуется использовать сохранённые сведения файлов кэша.
- SQLite сохраняет полный `AnalysisResult` в `snapshots.result_json`, версии правил и анализатора — в отдельных полях. Нормализованная таблица diagnostics из общей архитектуры пока не реализована.
- Сведения об entry points, framework conventions и динамически вычисляемых путях неполны. Нулевое число входящих импортов не доказывает неиспользование файла.

## Объём первой реализации

| Правило | Что вычисляем | Как объясняем |
| --- | --- | --- |
| `dependency-cycle` | SCC файлов, отдельно для статических исполняемых импортов и полного графа | Состав компоненты и один реальный замкнутый маршрут с исходными рёбрами, типами импортов и строками |
| `high-fan-out` | Число уникальных внутренних файлов, прямо импортируемых файлом | Фактическое значение, применённый порог, список целей; сигнал для ревью, не доказанный дефект |
| `high-fan-in` | Число уникальных внутренних файлов, импортирующих файл | Показывать как концентрацию потребителей с уровнем info; популярный общий модуль сам по себе не ошибка |
| `no-known-consumers` | Исходные файлы без входящих связей во всём известном графе | «Не найдены потребители», низкая уверенность в предположении о неиспользовании; без рекомендации удалить |
| `resolution-*` / `parse-error` | Адаптация имеющихся сведений resolver и синтаксического покрытия | Отдельная категория качества анализа; сохраняются причины, варианты и ссылки на источник |

Исполняемый граф для первого правила включает `import`, `reexport`, `commonjs_import`; type-only и dynamic import остаются в полном графе и явно указываются в доказательстве. Статический цикл означает цикл зависимостей, но сам по себе не доказывает ошибку выполнения. SCC полного графа, совпадающая по составу с уже показанной статической SCC, не создаёт вторую одинаковую карточку; дополнительные виды рёбер указываются в её evidence.

Fan-in/out считают уникальных соседей, исключают npm-пакеты, самоссылки и type-only связи. Несколько импортов одного файла не увеличивают показатель. Исходный список импортов доступен как evidence. Не вводим общий «балл качества» и метрику CBO: имеющаяся модель файлов не даёт оснований выдавать её за анализ классов.

Для `no-known-consumers` не выдавать предупреждения на известные entry points из `main`, `module`, локальных `exports` и `bin`, тесты, `.d.ts` и конфигурационные файлы. Эти исключения уменьшают шум, но не обеспечивают полноты: convention-based routes, плагины и динамические загрузчики остаются ограничением. Такие результаты всегда информационные, с описанием покрытия.

Размер файла можно показывать в карточке метрик, но отдельное правило «большой модуль» отложить: текущий счётчик включает комментарии и пустые строки, без оценки сложности это слабый сигнал.

## Контракт диагностики

Добавить типизированный массив `diagnostics` в `AnalysisResult` и метаданные прогона правил:

```text
Diagnostic {
  id, ruleId, severity: info | warning | error,
  confidence: confirmed | heuristic,
  category: architecture | coverage,
  title, explanation, suggestion,
  nodeIds[], evidence: Cycle | Coupling | Consumers | Resolution | Parse
}

RulesRun {
  version, configHash, effectiveConfig,
  completedRules[], skippedRules[{ruleId, reason}]
}
```

`confirmed` означает подтверждённость утверждения, а не гарантированный вред. Например, существование цикла подтверждено, влияние на поведение программы требует оценки. Confidence не заменяет severity. Для неизвестного покрытия нельзя показывать «проблем нет».

Для cycle evidence хранить компоненту и реальную последовательность рёбер: source, target, kind, line. Маршрут строить итеративно, детерминированно, без перечисления всех простых циклов. Для большой SCC хранить полный состав и один маршрут; UI загружает список частями и сообщает его размер.

Для coupling evidence хранить observed, threshold и уникальные nodeIds соседей. Для consumers evidence — проверенные исключения и известные ограничения. Не привязывать историческую диагностику к текущему состоянию файловой системы.

ID детерминирован внутри версии правил: хеш ruleId и отсортированных относительных идентификаторов затронутых узлов. Для диагностик импорта добавить specifier и source location. Межснимочное сопоставление и статус «новая/исправленная» отложить до отдельной работы с историей.

## Устройство Rules Engine

Добавить `diagnostics.rs` с типами и одной функцией `evaluate` над полным графом, покрытием и настройками. Перед прогоном построить индексы узлов и входящих/исходящих соседей; переиспользовать существующий итеративный поиск SCC. Не создавать plugin runtime или DSL.

Порядок: индексирование → кэшируемый AST-разбор → разрешение импортов → построение графа → правила → атомарное сохранение снимка. Сбой обязательного правила не публикует новый снимок; отключённые или неприменимые правила имеют явный статус. Сохраняется последний успешный результат.

Для первого релиза достаточно небольшого необязательного `dependency.config.json`: enabled/exclude для правил и пороги fan-in/out. Только статический JSON; валидация схемы и ограничение размера, отсутствие выполнения кода. Ошибки конфигурации объяснять до публикации результата; не подменять неверный порог значением по умолчанию молча. Исключения правил не меняют граф и индексирование.

Стартовые пороги — настраиваемые ориентиры, не универсальные нормы. Зафиксировать значения после прогона fixtures и нескольких доступных реальных репозиториев с разными структурами; в каждой карточке показывать фактический порог. Не применять скрытые percentile-пороги, из-за которых смысл результата меняется при добавлении несвязанных файлов.

## Снимки, версии и совместимость

- Сохранить JSON-снимки и текущую SQLite-транзакцию; отдельная SQL-модель диагностики пока не оправдана имеющимися запросами.
- Новые поля читаются из старых снимков через defaults. Отсутствие метаданных прогона означает «расширенная диагностика не выполнялась», а не ноль нарушений.
- Старые снимки показывают имеющиеся SCC/ошибки resolver с пометкой legacy. Их нельзя изображать как произвольную последовательность цикла или незаметно пересчитывать по новым правилам.
- Версия rules меняется; версия parser остаётся прежней, если формат извлечённых импортов не изменился. Изменение конфигурации правил пересчитывает правила и resolution, но не инвалидирует AST неизменившихся файлов.
- Эффективная конфигурация и её хеш сохраняются в новом снимке вместе с результатом; история остаётся воспроизводимо объяснимой после изменения настроек.

## Интерфейс

Problems становится списком диагностик с фильтрами rule/severity/category и явными метаданными покрытия. Карточка: утверждение → основание → ограничения → возможное действие. Общий счётчик учитывает архитектурные предупреждения отдельно от неполноты анализа; info не выдаются за критичные ошибки.

Переход «Показать в графе» передаёт набор nodeIds диагностики, а не только один выбранный файл. Это небольшое расширение модели представления 0.4: подсветить SCC или coupling-окружение, сохранить доступ к полной карточке и показать число скрытых элементов, если действует лимит рисунка.

Подавление диагностик, пользовательские слои архитектуры, экспорт отчётов и сравнение снимков не входят в обязательный объём 0.5.0.

## Порядок реализации и критерии готовности

1. Типы diagnostics/RulesRun, обратная совместимость и адаптация существующих ошибок разрешения/разбора.
2. SCC и доказательные маршруты; исправление legacy-отображения циклов. Fixtures: SCC, в которой алфавитный порядок не образует цикл, self-loop, type-only cycle, mixed cycle, dynamic-only cycle и длинная цепь без рекурсии.
3. Уникальные fan-in/out и no-known-consumers с защитой entry points. Fixtures: повторные импорты, barrel reexports, package entry points, тесты, декларации, неполное покрытие, исключения и неверная конфигурация.
4. Фильтры Problems и переход к набору узлов в графе; ручная проверка на Windows, включая пустой и большой результат.
5. Проверить сохранение/переоткрытие диагностик, неизменность старых снимков, отсутствие публикации при ошибке записи и reuse AST после изменения только правил/конфигурации.
6. Прогоны на доступных реальных проектах: записать размер/покрытие, время правил, число сигналов и причины ложных срабатываний; по результатам выбрать и документировать стартовые пороги.

Готовность: каждая карточка воспроизводима по сохранённому снимку, все заявленные связи подтверждаются рёбрами, эвристики явно обозначены, сбой не портит историю, неизменившиеся исходники повторно не разбираются. Impact Analysis и Git Integration остаются следующими этапами.
