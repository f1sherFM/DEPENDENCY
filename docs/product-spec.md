# DEPENDENCY
## Complete Product Specification
**Версия концепции:** 1.0  
**Тип:** Desktop Developer Tool  
**Целевая платформа:** Windows 10/11  
**Основная задача:** Анализ структуры, зависимостей и архитектуры программных проектов.

---

# 1. Общая концепция

DEPENDENCY — настольное приложение для комплексного исследования программных проектов.

Пользователь выбирает локальный репозиторий, после чего приложение анализирует его структуру, исходный код, зависимости и архитектурные связи.

Результат анализа представлен в нескольких формах:

- Интерактивный граф зависимостей.
- Иерархическая структура проекта.
- Список модулей и компонентов.
- Анализ внешних библиотек.
- Список архитектурных проблем.
- Анализ потенциального воздействия изменений.
- Статистика и отчёты.

Приложение должно не только находить проблемы, но и объяснять их происхождение, последствия и возможные способы исправления.

Основной принцип: пользователь должен иметь возможность перейти от общей картины проекта к конкретному файлу, импорту, зависимости или проблеме.

# 3. Dependency Graph

Центральный функциональный модуль DEPENDENCY.

Представляет программный проект в виде интерактивного графа.

### 3.1 Типы узлов

Граф должен поддерживать несколько типов объектов:

- Файлы.
- Модули.
- Каталоги.
- Компоненты.
- Внешние библиотеки.
- Пакеты.
- Точки входа.

Каждый тип должен иметь собственное визуальное обозначение.

### 3.2 Типы связей

Необходимо различать:

- Прямой импорт.
- Реэкспорт.
- Type-only import.
- Динамический импорт.
- Зависимость между пакетами.
- Зависимости сборки.
- Зависимости тестовой среды.

Тип связи должен определять оформление ребра графа.

Нельзя смешивать разные виды зависимостей в одну неразличимую категорию.

### 3.3 Взаимодействие с графом

- Масштабирование.
- Перемещение по рабочей области.
- Выбор узлов.
- Множественный выбор.
- Перетаскивание узлов.
- Поиск файлов и модулей.
- Подсветка связей выбранного узла.
- Переход к исходному файлу.
- Просмотр информации о соединении.
- Фокусировка на выбранной части графа.
- Навигация по истории выбранных объектов.

### 3.4 Режимы отображения

Предусмотреть несколько представлений:

**Full Graph**

Полная карта зависимостей проекта.

**Module Graph**

Связи между логическими модулями.

**Package Graph**

Внешние библиотеки и их зависимости.

**Directory Graph**

Связи между основными каталогами.

**Dependency Flow**

Направление распространения зависимостей.

**Problem Focus**

Граф, на котором выделены циклы, проблемные связи и потенциально неиспользуемые компоненты.

### 3.5 Фильтрация

Пользователь должен иметь возможность скрывать или показывать:

- Внутренние модули.
- Внешние библиотеки.
- Тестовые файлы.
- Конфигурационные файлы.
- Type-only связи.
- Динамические импорты.
- Отдельные каталоги.
- Различные уровни вложенности.

### 3.6 Работа с крупными графами

При большом количестве узлов приложение должно поддерживать:

- Группировку узлов.
- Сворачивание каталогов.
- Выбор глубины отображения.
- Локальный граф выбранного модуля.
- Мини-карту.
- Поиск и подсветку узлов.
- Отображение только выбранных связей.

Граф должен оставаться управляемым на крупных репозиториях.

# 5. Code Analysis

Модуль статического анализа исходного кода.

Это один из важнейших компонентов приложения.

### 5.1 Циклические зависимости

Обнаружение циклических связей между:

- Файлами.
- Модулями.
- Пакетами.
- Каталогами, если связи можно агрегировать корректно.

Для каждого цикла показывать:

- Полную последовательность узлов.
- Все связи, формирующие цикл.
- Место возникновения каждой связи.
- Количество затронутых файлов.
- Возможные варианты устранения.

Поддерживать выделение циклов непосредственно в графе.

### 5.2 Неиспользуемые модули

Поиск потенциально неиспользуемых компонентов.

Проверять:

- Файлы без известных входящих зависимостей.
- Неиспользуемые экспорты.
- Неиспользуемые импорты.
- Неиспользуемые внешние пакеты.
- Неиспользуемые исходные модули.

Учитывать известные точки входа и конфигурационные механизмы.

Результаты должны иметь уровень уверенности. Динамические импорты, reflection, плагины и runtime-регистрация могут делать некоторые зависимости невидимыми статическому анализатору.

Не объявлять модуль неиспользуемым без достаточных оснований.

### 5.3 Чрезмерная связанность

Выявление модулей, от которых зависит слишком большое количество других компонентов.

Показывать:

- Fan-in.
- Fan-out.
- Количество входящих зависимостей.
- Количество исходящих зависимостей.
- Центральность в графе.
- Связность с другими архитектурными слоями.

Позволять находить компоненты, превращающиеся в центральные точки отказа.

### 5.4 Проблемные компоненты

Обнаружение:

- Чрезмерно больших модулей.
- Слишком глубоких цепочек зависимостей.
- Повторяющихся связей.
- Сильно связанных между собой компонентов.
- Нарушений архитектурных границ.
- Неоднозначных импортов.
- Неразрешённых зависимостей.
- Неверных путей импорта.

### 5.5 Анализ сложности

Для поддерживаемых языков рассчитывать:

- Количество строк кода.
- Цикломатическую сложность.
- Количество функций и методов.
- Количество классов и структур.
- Количество импортов.
- Количество экспортов.
- Размеры модулей.

Необходимо различать реальные AST-метрики и приблизительные эвристические оценки.

### 5.6 Архитектурные правила

Пользователь должен иметь возможность определять собственные правила:

- Какие модули могут импортировать друг друга.
- Какие каталоги должны оставаться независимыми.
- Какие слои могут обращаться к другим слоям.
- Какие зависимости запрещены.
- Какие библиотеки разрешены или запрещены.

При нарушении правил создавать диагностическую запись с объяснением.

# 6. Impact Analysis

Модуль анализа последствий изменений.

Позволяет определить, какие части проекта могут быть затронуты изменением конкретного компонента.

### 6.1 Анализ выбранного файла

При выборе файла отображать:

- Прямые зависимости от него.
- Транзитивные зависимости.
- Зависимые модули.
- Зависимые компоненты.
- Потенциально затронутые тесты.
- Связанные внешние интерфейсы.

### 6.2 Анализ изменения экспортов

Для поддерживаемых языков анализировать:

- Изменение экспортируемых функций.
- Изменение классов и типов.
- Удаление экспортов.
- Переименование сущностей.
- Изменение публичных интерфейсов.

Показывать потребителей изменённых сущностей.

### 6.3 Оценка риска

Формировать объяснимую оценку потенциального риска изменения.

Учитывать:

- Количество зависимых компонентов.
- Глубину распространения изменений.
- Количество затронутых публичных интерфейсов.
- Наличие циклических зависимостей.
- Архитектурную критичность модуля.
- Наличие связанных тестов.

Не выдавать эвристическую оценку за гарантию реальных последствий. Показывать факторы, на основании которых сформирован результат.

# 7. Package Intelligence

Полноценный анализ внешних библиотек.

### 7.1 Обнаружение пакетов

Находить зависимости через конфигурационные файлы и lock-файлы соответствующих экосистем.

Поддержать:

- npm.
- pnpm.
- Yarn.
- Bun.
- Cargo.
- Python: pyproject.toml, requirements.txt и поддерживаемые lock-файлы.

### 7.2 Информация о пакетах

Для каждой библиотеки показывать:

- Название.
- Текущую версию.
- Источник зависимости.
- Прямую или транзитивную зависимость.
- Production или development.
- Количество зависимых пакетов.
- Связанные файлы проекта.

### 7.3 Анализ пакетов

Выявлять:

- Дублирующиеся версии пакетов.
- Несовместимые диапазоны версий.
- Неиспользуемые прямые зависимости.
- Потенциально устаревшие пакеты.
- Проблемные зависимости.

### 7.4 Внешняя информация

При наличии интернет-соединения предоставлять:

- Доступные обновления.
- Информацию об известных уязвимостях из актуальных источников.
- Лицензии пакетов, если информация доступна.
- Сведения о состоянии поддержки пакетов.

Онлайн-проверки должны быть отдельными от локального анализа.

DEPENDENCY не должен автоматически устанавливать обновления или изменять файлы управления пакетами.

# 13. Производительность и архитектура

Основной принцип: анализ проекта должен быть быстрым, локальным и ресурсоэффективным.

Требования:

- Парсинг исходного кода без выполнения пользовательского кода.
- Инкрементальный анализ.
- Кэширование результатов.
- Обработка больших репозиториев.
- Фоновая обработка.
- Отмена анализа.
- Отслеживание ошибок.
- Эффективная визуализация крупных графов.
- Хранение локальной базы результатов.
- Повторное использование неизменившихся результатов.

Предпочтительная технологическая основа:

- Tauri 2.
- Rust.
- React.
- TypeScript.
- Локальная база SQLite.
- AST-парсеры и языковые анализаторы.
- WebGL или Canvas-рендеринг крупных графов.

Конкретные библиотеки выбирать исходя из качества поддержки, производительности и совместимости.

# 14. Приватность и безопасность

DEPENDENCY — локальный инструмент.

По умолчанию:

- Исходный код не отправляется в облако.
- Аккаунты не нужны.
- Нет обязательной регистрации.
- Анализ выполняется локально.
- Результаты сохраняются на устройстве.

Внешние сетевые запросы разрешены только для явно включённых функций получения информации о пакетах и уязвимостях.

Анализатор не должен запускать исследуемый проект или выполнять содержащиеся в нём скрипты.

По умолчанию приложение работает в режиме чтения.

Автоматическое исправление исходного кода не входит в обязательный функционал.

# 15. Критерии завершённости

Полная версия DEPENDENCY считается реализованной, когда пользователь может:

1. Открыть реальный локальный репозиторий.
2. Получить его структурную модель.
3. Просмотреть интерактивный граф зависимостей.
4. Исследовать любые поддерживаемые модули.
5. Найти циклические связи.
6. Обнаружить подозрительные и неиспользуемые компоненты.
7. Исследовать внешние библиотеки.
8. Оценить потенциальное воздействие изменения файла.
9. Сравнить архитектуру разных версий проекта.
10. Изучить метрики и сформировать отчёт.
11. Перейти от найденной проблемы непосредственно к исходному коду.
12. Повторить анализ без необходимости полностью переиндексировать неизменившийся проект.

Все функции должны работать на реальных проектах и реальных данных.

Интерфейс, демонстрационные графы и тестовые показатели не могут считаться реализованным функционалом.

# 16. Принципы разработки

- Не создавать монолитное приложение.
- Не переусложнять архитектуру.
- Не внедрять искусственные ограничения количества файлов или связей.
- Не скрывать неполноту анализа.
- Показывать источник и основание каждой диагностики.
- Разделять подтверждённые проблемы и эвристические предупреждения.
- Обеспечивать расширяемость языковых анализаторов.
- Поддерживать корректность результатов важнее количества метрик.
- Не реализовывать функции-заглушки.

Главная цель — создать полноценный инженерный инструмент, который позволяет понимать архитектуру программного проекта и принимать обоснованные технические решения.
