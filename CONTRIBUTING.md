# Изменения в DEPENDENCY

Проект развивается под рабочий процесс владельца. Изменения должны решать конкретную задачу. Новые зависимости и универсальные абстракции требуют практического обоснования.

Перед изменением прочитай [инструкцию разработки](docs/development.md) и относящийся к задаче код. Сохраняй пользовательские файлы и настройки.

## Качество

- Исследуемые проекты не запускаются ради анализа: без install/lifecycle hooks, build scripts, macros, setup.py и исполняемых конфигураций.
- Ошибка анализа/записи не должна уничтожать последний успешный снимок. Не пересчитывай историю неявно.
- Для нового поведения добавь содержательный regression test: fixture должен показывать, какую ошибку он предотвращает.
- Для изменения parser/resolver/rules/storage проверь версии и чтение старых данных. App version не заменяет версии форматов.
- Запусти проверки из README. UI проверяй через пользовательские сценарии; mocked transport не равен проверке native IPC или установщика.

## Описание результата

Укажи проблему, новое поведение, выполненные проверки и ограничения. Отделяй результаты от предположений. Скриншот добавляй, когда он помогает оценить UI.

Не включай в Git базы SQLite, личные проекты, токены, .env и установщики из target. Минимальные воспроизводимые fixtures предпочтительнее исходников закрытого проекта.

Коммиты делай по законченной задаче. Push, теги и релизы — отдельные действия по согласованию с владельцем. CI ничего не публикует автоматически.
